# G2: explicit airline policy conditions

G2 is a rule-based, per-call baseline. It runs Python predicates before a sensitive
tool executes. It does not call an LLM to interpret policy, maintain a fact store
between checks, or use a SAT/SMT solver. Each check reconstructs its inputs from
the supplied transcript. The agent's prompt and the shared G1 execution wrapper
are unchanged.

## Coverage

Rules implement the current `data/tau2/domains/airline/policy.md` and domain API.

| Tool | Conditions |
|---|---|
| `book_reservation` | User-supplied ID and matching user profile; valid itinerary and cabin; available seats/prices; 1–5 passengers with names and birth dates; correct baggage allowance; insurance choice; saved payment methods with sufficient balances, nonnegative amounts, no duplicate methods, at most 1 certificate, 1 credit card, 3 gift cards; payment total equals fares plus $50/extra bag and $30/passenger insurance; confirmation matching all action details |
| `cancel_reservation` | Matching active reservation; user-supplied owner ID; cancellation reason; all segment statuses known and none flown; at least one exception (0–24h booking age, airline cancellation, business cabin, insurance with health/weather reason); target cancellation confirmed |
| `update_reservation_flights` | Matching active reservation and owner ID; basic economy cannot change dated flight segments, but can change cabin; cabin changes require no flown segment; connected itinerary preserves origin/destination/trip type; new flights have seats and current prices; unchanged segments retain their original prices; saved credit/gift card covers the computed difference or receives the refund; exact flights/cabin/payment/difference confirmed |
| `update_reservation_baggages` | Matching active reservation and owner ID; bags cannot decrease; paid bags match the membership/cabin allowance; saved credit/gift card covers $50 per added paid bag; total bag count, payment and charge confirmed |
| `update_reservation_passengers` | Matching active reservation and owner ID; passenger count unchanged; complete valid passenger identities; new names and dates of birth confirmed |
| `send_certificate` | User explicitly requested compensation and complained of the relevant disruption; verified affected reservation belongs to that user; silver/gold membership, insurance, or business cabin; airline cancellation → $100/passenger; verified delay plus completed flight change/cancellation → $50/passenger; exactly one matching incident; no repeated grant for the same reservation/disruption |

The backend API has no post-booking insurance-update operation. Extra arguments
such as `insurance` on a modification are rejected by the argument schemas.
Existing backend constraints (payment totals, seats, passenger count) are checked
before execution as well as policy constraints the backend omits.

The compensation reuse rule interprets the fixed per-passenger amount as one
grant per reservation/disruption in a simulation. It does **not** limit a user to
one certificate across distinct reservations. Ambiguous incident association is
blocked. This operational interpretation should be reported alongside results.

## Inputs and confirmation

`airline_evidence.py` matches successful tool results to unique preceding
assistant tool-call IDs and checks returned reservation/user IDs. User messages
and pending calls cannot establish record facts. Flight searches provide route,
seats, prices and available status; `get_flight_status` supplies other statuses.
Successful writes replace affected reservation snapshots and invalidate affected
payment/seat snapshots. Failed writes invalidate snapshots conservatively because
some backend operations can partially mutate before raising.

For delay compensation, the checker inspects completed calls and the booking and
flight statuses that preceded them. Historical certificate calls are inspected
similarly to prevent repeated grants. All of this is reconstructed locally from
the transcript on each check, not stored across checks. This is the minimum
history needed for the policy's “after changing or cancelling” condition.

`airline_dialogue.py` deterministically parses user intent/confirmation:

* The user must supply the owner's exact ID. This is a benchmark identity check,
  **not authentication**; no login protocol is provided by this environment.
* Cancellation reasons recognize health/weather, changes of plan, and explicit
  reason/because statements. Negated health statements cannot prove coverage.
* Confirmation must answer an assistant proposal with an unambiguous affirmation
  such as `yes`, `yes please`, `yes, please proceed`, `go ahead` or `I confirm`.
  The parser also accepts descriptive affirmative prose grounded in the call's
  values, including curly apostrophes; unknown values or override requests fail.
  The proposal must identify the reservation and action-specific values. Booking
  requires passenger names and birth dates. Passenger changes require the changed
  fields and target name; unchanged passenger fields need not be repeated.
* Dated flights, cabin, bag count, insurance selection, payment IDs (or saved
  credit-card last four digits), and charge/refund amount must match as applicable.
  Zero amounts may be disclosed as “no additional fees/charges/payment”, including
  “no extra baggage fees”.
  A zero-cost modification need not disclose the unused payment ID in its
  confirmation, but the backend profile must still contain that eligible method.
  Structured JSON argument proposals are compared by key/value bindings.
* Refund/charge wording (v7): a user reply may restate amounts and payment
  types, but every stated dollar amount must equal one computed for the call
  (charge/refund difference, booking allocations, or a cancellation's net
  payment-history refund) and every named payment type (gift card, credit card,
  certificate) must be used by the action — for cancellation, the booking's
  original methods. A reply asking to cancel cannot approve another action.
  “Original payment method” identifies a method only when the reservation's
  payment history has exactly one charged method equal to the call's
  `payment_id`; generic “gift card”/“certificate”/“credit card” only when the
  profile holds exactly one method of that type. A cancellation proposal that
  promises a refund different from the payment-history total is rejected.
* Reads between approval and execution are allowed. A later user turn replaces
  approval. A prior attempt of the same action type consumes it; another action
  type explicitly included in the same proposal can still be executed.

A failed confirmation condition is reported as
`explicit confirmation of this action and its parameters: ...` followed by the
value-level gaps: what the proposal before the user's latest reply omits
(e.g. `reservation M05KNL; the refund of $2571`), what it contradicts, and which
reply words/amounts/payment types are unbound. In `g2_feedback` this text is the
agent's repair instruction. Values come only from the call and transcript tool
results. Group logs by the stable prefix.

These English parsers are deliberately conservative and are **not a complete
semantic understanding system**. Complex wording can be misinterpreted, and
legitimate summaries omitting checked details can be blocked. Log categories
`dialogue`, `evidence`, `schema` and `policy` distinguish these causes. Do not
equate synthetic tests with a measured false-positive rate or adaptive-attack
resistance. The guard covers tool execution, not every conversational policy
such as avoiding subjective recommendations.

Policy time comes from the policy's fixed EST clock, not the host clock. The
v6 parser also uses that clock's year for month/day expressions without a year.
Booking confirmations may state payment allocations without repeating their sum;
allocations must match each method's amount, and any stated total must agree.
Free-bag wording is recognized only alongside the independent allowance check.
The rules are specific to the current airline policy; changes to that policy require
reviewing the encoded conditions. Other domains are rejected by the factory.

## Running and comparing

Four registered agents share G1's handling modes:
`g2_replan`, `g2_feedback`, `g2_notify`, `g2_terminate`.
`guard_max_replans` is supported. Judge-model options, `guard_tools` overrides and
fail-open options are rejected so they cannot silently bypass G2 coverage.

In `g2_feedback`, missing profile evidence now names the exact
`get_user_details(user_id=...)` query to run. The agent must actually execute
that query; the guard does not fill missing facts from hidden backend state.

Example of a small **paid** training smoke run (requires API/network authorization):

```bash
tau2 run --domain airline --task-split-name train --task-ids 12 40 \
  --agent g2_feedback --agent-llm gpt-4.1-2025-04-14 \
  --user-llm gpt-4.1-2025-04-14 --num-trials 1 --max-concurrency 1 \
  --max-steps 40 --timeout 180 --save-to g2_train_smoke_v2
```

For G0/G1/G2 comparisons use identical task splits, model settings, trial counts,
and handling modes; pin the code version. Use train only to refine rules and
parsers, then freeze them before evaluating test. Guard decisions include
per-condition evidence/categories, resolved coverage/version, latency, and zero
judge cost. Agent and simulated-user model calls still cost money.

Existing trajectories can be checked **without model calls**:

```bash
python -m tau2.guards.offline_eval data/simulations/<run> \
  --domain airline --guard g2 --repeats 2 --out g2_offline.json
```

This reuses exactly the same attempt extraction used by G1. The labels `gold`,
`forbidden` and `other` are task-action proxies; they are not independently
verified policy ground truth. A gold call can be premature. This offline report
does not measure counterfactual task completion or attack success rate.

## Validation

```bash
pytest tests/test_guards tests/test_domains/test_airline -q
```

Tests include legal and illegal calls for all tools, the nine baggage allowance
combinations, time boundaries, basic-economy cabin vs. flight changes, prices,
refund direction, payment/confirmation mismatches, fabricated record claims,
missing/failed/pending results, compensation eligibility and ordering, and repeat
compensation. Integration tests execute every write through `GuardedAgent` and
real airline tools, verifying both strict and lenient database replay; rejected
calls never reach replay. All these tests use scripted messages, not paid models.

Free-form model smoke runs and full normal/adversarial benchmark metrics remain
separate experimental validation, not something the local test counts establish.

Training smoke rounds and repairs are documented in
`src/experiments/guards/audits/g2_train_smoke.md`. V2/v3 passed 0/2;
the real v4 run passed task 40, while task 12 failed because its agent did not
retrieve user-profile evidence. V5 improves actionable feedback and parsing;
the subsequently authorized v5 task-12 run passed with verified profile evidence,
one allowed write, zero blocks and zero guard errors. Task 40's observed success
is under v4, so these results are not a two-task v5 pass rate. Current guard/airline
tests: 200 passed. These small training runs do not establish held-out performance
or adaptive-attack resistance.

The later four-task v5 training batch passed 1/4 and is audited separately in
`src/experiments/guards/audits/g2_train_expand.md`. V6 fixes a booking-confirmation
defect, passes 210 guard/airline tests, and produces the gold booking database in
a scripted historical-call execution. V6 has not been run in a new paid model
conversation. Refund-confirmation parsing and task/simulator errors remain
outstanding; these results are not a full benchmark comparison.

V7 (refund-confirmation binding and diagnostics) passes 225 guard/airline tests.
On the same 12 recorded v5 attempts it still allows 4/4 exact-gold calls; three
task-11 business-class cancellations that v6 blocked only for refund wording are
now allowed (policy-compliant but not the task's gold downgrade, so the task would
still fail). Task-15 calls remain blocked with specific missing values. V7 has
not been run in a paid model conversation.

A paid v7 run of train tasks 15 and 20 passed task 15. Task 20 failed: G2
correctly blocked an overcharge for a gold member's free bags, then falsely
blocked the corrected gold call over “Total checked bags: 3”. V8 accepts this
label form and no longer treats “do not need to pay” as refusal (232 tests).
See `src/experiments/guards/audits/g2_train_expand.md`. V8 is unrun with models.
